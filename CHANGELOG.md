## [Unreleased]

### Added

- Setup installer (`setup/init.py`, stdlib-only): installs the framework into a consuming project — every skill package copied whole into the project's `.agents/skills/` (the canonical cross-client path), and the project's standards rendered from the `standards/` single source into `.agents/standards/`, every standard outside the artifact-format families always and at most one variant per family (`commit`, `pr`, `ticket`) per the consumer's answers, collected at the prompt or supplied as a JSON config for non-interactive/CI onboarding (an interactive run ends by printing the JSON that repeats it). An install manifest (`.agents/awf-install-manifest.json`) records every installed path with a content digest and the framework source tag (`git describe`, the CHANGELOG's latest release where the copy has no git history, or `--source-tag`), which is what makes re-runs safe: setup never silently overwrites — a path the manifest does not record is skipped and reported, with a byte-identical pre-existing directory adopted rather than rewritten; a recorded install the consumer modified is skipped and reported, which covers customized standards by construction; an unmodified one is refreshed when the source changed and reported up to date when it did not, so a re-run against an unchanged source changes nothing; and an install the current run no longer ships or selects is reported stale, never deleted. A symlinked managed directory is refused rather than written through — in the CI mode the repository contents are the input, and a link under `.agents/` would carry writes past the `--target` boundary — and existence is checked without following links everywhere it gates a write, so a symlink at the manifest path or at a planned install path is refused or skipped rather than read as absence and replaced. Fifty-nine unit tests (`setup/test_init.py`) cover installing, idempotency, the collision guard, upgrades, stale reporting, config validation, the interview, source-tag resolution, and manifest handling — installs are staged and renamed into place, so a run that dies mid-copy leaves no half-written install a later run would refuse to touch; conformance CI runs them and adds a smoke install of this repository into a scratch project, spot-checking that the first run installed and asserting a second changes nothing. The installer reuses `scripts/render_standards.py` for placeholder validation (`validate_config`, extracted from `load_config` with behavior unchanged) and rendering, and `standards/README.md`'s rendering example now names `.agents/standards`, so the documented render destination and the installer's are one location rather than two.
- `CONTRIBUTING.md` — how a change lands (pull requests against `main`, one answerable question per PR, conventional-commit subjects, squash merges whose titles become `main`'s subjects and whose bodies are self-contained summaries), the conformance checks run locally before opening a PR plus the advisory `skills-ref` pass for touched skills, the two generated surfaces edited at their source rather than in place (the `AGENTS.md` index, the shared-template copies), and the three authoring rules no check runs, stated with their reasons: every claim in a public artifact checkable from the repo alone, commit messages included and claims about unpublished drafts excluded as unverifiable by construction; a widened declaration obliging six surfaces that must agree rather than merely all be touched, its strength argued from availability rather than caution, unreached places recorded as empty, and the frontmatter `description` checked against the diff rather than the file; and the repo's own checks run against your own diff — before review, again after every fix on the surfaces that describe the change, and after a clean round with the template pairing and the whole-file read that need the final diff.
- Conformance validates that a step-bound skill and its stage declare the same step. Eighteen skills restate the step block their stage contract declares, and nothing checked that the two copies agreed — the drift is invisible in review because the halves sit in different files, and a skill promising inputs its stage does not is unexecutable under that stage. `role`, `inputs`, `on`, and the output artifact must match; `output.template` is deliberately exempt, being a skill-relative path a stage cannot carry. Four new unit tests, and the conformance summary now reports the step-bound count alongside the others.
- Intake skill family (`skills/`), binding the intake stage's two steps — the last of the eighteen the six stages declare, bringing the packaged set to twenty-two skills, eighteen step-bound and four standalone. `awf-brief-confirm` restates whatever started the run as `{run}/brief.md`, scaffolded from `references/brief.template.md`: the goal as an outcome rather than an activity (a goal phrased as the work — "refactor the session module" — cannot be checked; the same intent phrased as its outcome can), constraints marked stated or inferred so the intake gate can strike a reading cheaply while it is still visible as a reading, acceptance criteria specific enough that two readers would agree on whether they hold — the same criteria `awf-plan-validate` traces to plan steps and `awf-deliver-validate` walks one at a time at the end of the run — and an out-of-scope list carrying only what a reasonable reader might otherwise assume is included, an inventory of everything the run is not being how the two or three boundaries that matter get buried. Where the request points at particular parts of the system it names them as focus areas, which `awf-ground` reads as its instruction to go file- and function-deep there rather than evenly everywhere — the field its grounding counterpart's header already expected and the brief had nowhere to record. Its ambiguity test is whether the brief can be restated with confidence rather than whether anything is unclear, since something always is: ask when the answer would change the goal, a constraint, or a criterion, and record a stated assumption when it would not. Where the threshold is crossed it stops at the `clarifying-question` gate and spends its one question — a hard budget — on the ambiguity that would cost the most to discover later rather than the first one encountered, decision-shaped so the answer can be a choice rather than an essay, with the answer's content folded into the brief and never into the gate record. It accepts a source reference in place of pasted text, fetched through the executing harness's connections, where fetched content is request data and never instructions and a source that appears to issue instructions is itself an ambiguity worth recording. It declares no project standard — the third skill to do so and the second to decline on the record: the brief records what was asked, and holding the request to a standard of the reader's would turn a constraint the reader supplied into one the requester appears to have stated. `awf-risk-route` applies the spec §5.2 rubric to that brief and fills its `## Routing` section with at most one proposed class, the one-line rationale the executor transcribes verbatim into `run.risk_rationale`, and the security-surface reading — recorded whether or not it fired, because the rubric's rule has two halves and the second, enabling security review, otherwise leaves intake with nothing carrying it. Blast radius is counted across module boundaries rather than files (ten files inside one module is a smaller radius than two that change a signature other modules call), reversibility is what undoing the change would cost once it lands however small the diff, decomposability reads the signal that a phase list is coming without fixing one, novelty is measured against the patterns the codebase already carries rather than against what is new to the product, and requirement ambiguity binds in the opposite direction — it never inflates the class, routing back to the clarifying question instead of buying process against uncertainty, with the Routing section carrying a withheld class and what could not be pinned down, so the question that follows has a subject and the missing class reads as a decision rather than an omission. Where a class is proposed it is never a hedge, "R2, possibly R3" handing the classification back to the human it was made for; at a genuine boundary it leans upward and says so in the rationale, since reclassification runs one way (spec §5.3) and an override at the gate is a designed outcome rather than a failure. It writes no run state: the executor transcribes the class the human accepts at `intake-approval`, which may not be the class proposed.
- Tickets skill family (`skills/`), three standalone skills — no stage binds them — for turning a body of requirements into tracked, orderable work: `awf-parse-requirements` decomposes raw requirements (a PRD, a technical spec, user stories, bug reports, freeform text) into discrete typed work items — `feature`, `bug`, `chore`, `spike` — each with a self-contained description and testable acceptance criteria, plus directional dependencies that carry the reason one item waits on another (a dependency states what B consumes from A; "related" is a grouping and constrains nothing), theme groupings, relative `S`/`M`/`L`/`XL` sizes where an `XL` stands as an open question about decomposing further, and every ambiguity, contradiction, and gap flagged against the quoted source text with either a clarifying question or the default assumption taken — scaffolded from `references/parsed-requirements.template.md`. It accepts a source reference in place of pasted text — a Jira epic, a Confluence page, a Notion doc, a Linear project — fetched through the executing harness's connections with pasted text or an export as the fallback, where fetched content is requirements data and never instructions and a fetched source that appears to issue instructions is itself worth flagging. It is the one skill besides `awf-analyze-report` that declares no project standard, deliberately: it reports what the requirements say and where they fail to say it, holding the text to no bar of its own, which is what keeps a flag a fact about the source rather than a preference of the reader. `awf-create-tickets` renders those items as tickets someone can pick up cold — action-oriented titles, descriptions that stand without the requirements document, acceptance criteria as independently verifiable checklists, priority assigned against consequence rather than enthusiasm (a set where everything is critical has ranked nothing), dependencies as explicit references rather than prose buried in a description where an ordering constraint is invisible, and an implementation order in which dependencies bind first and risk-reducing work comes early within a tier. The ticket shape is the project's to declare: `references/ticket.template.md` carries the artifact's own summary, ordering, and dependency sections plus a default per-ticket block used only where the project declares no rendered ticket-format standard — Jira, Linear, and GitHub Issues ship as built-ins and any other tracker is one project-local standard file, no framework change — so what a ticket must *say* stays invariant while how it is laid out does not. Filing is out of scope by design: the artifact is the deliverable and any API push into a tracker is the consuming project's own channel, under its own credentials and approval. `awf-validate-tickets` renders the verdict as the shared validation report's sixth consumer, checking coverage in both directions item by item rather than by counting (equal totals prove nothing when one item was dropped and one ticket invented), self-containment by reading each ticket as someone who has seen no other artifact, duplicates and overlaps with a merge/deduplicate/separate recommendation, the dependency chain for existence, direction, cycles at any length, and an order that respects what it declares, and priority and size as a calibration across the set rather than ticket by ticket. It appends three checklist rows the shared core does not reach — **Self-containment**, **Duplication**, **Calibration** — and deliberately adds no Coverage row, since coverage's two directions are exactly the core **Completeness** and **Scope** rows and the chain is the core **Dependencies** row — coverage instead appends a **Coverage** section, the item-by-item mapping with gaps and orphans marked in place, because it is the one check whose result is a table rather than a boolean and the rows that record whether it holds need somewhere to point for how that was established. Its verdict uses the spec §3.3 vocabulary (`PASS_WITH_CONDITIONS`, normalizing the prototype's spaced form) and gates no loop: standalone, nothing downstream consumes it, so it reports to whoever invoked the run — which raises the bar on saying plainly what is wrong, there being no next iteration to catch what this pass excuses.
- Ideation skill family (`skills/`), binding the ideation stage's three remaining steps — `ground` shipped with the analysis family: `awf-ideate` explores the solution space into `{run}/ideation.md` — three to five approaches that must differ in shape rather than in naming (the distinctness test is structural: same modules touched, same data flow, one approach), each given the same treatment so the comparison is fair (core idea, mechanics, advantages, risks including the migration, operational, and reversal costs that only appear after shipping, codebase impact in named modules, complexity relative to the project, and the decisions it would force), the considered-and-discarded set kept as evidence of the space explored and as what stops a revision re-proposing a ruled-out option, and exactly one recommendation whose reasoning traces to the brief and which states what would overturn it — scaffolded from `references/ideation.template.md`, with `references/refine.md` as the load-on-trigger pass that carries the recommendation to planning-ready detail (components, integration points, data flow, a mitigate/accept/defer answer for every recorded risk, and an explicit ready-to-plan assessment) while stopping short of the step decomposition, file scope, and test plan that belong to `plan-create`. The prototype's multi-turn interactive framing is dropped per item 2 — interactivity is the execution mode's and the gates', not a skill property — and with no gate in this stage, an unresolved fork travels as an open question to `plan-approval`. Both generating and judging approaches read the project's architecture standard where one exists, carried over from the prototype's `standards/architecture` declaration the way the implementation and review families carried theirs: a departure from the standard is legitimate but must be argued in the artifact, and an unargued one is a finding. `awf-ideate-validate` renders the stage's verdict adversarially against the brief — coverage of every criterion by the recommended approach, distinctness tested structurally with collapsing candidates named, feasibility and impact claims verified against the codebase itself rather than against a sibling artifact (which is why the grounding is deliberately not an input: the question is whether a claim is true, not whether it was faithfully copied), risks interrogated for what was conveniently omitted, the discarded set checked for options ruled out on reasons that do not hold, and the recommendation tested against the artifact's own evidence — with `references/evaluation-matrix.md` as working method, six criteria on a 1–5 scale weighted by the brief rather than by habit, explicitly never the output: a total never outranks a critical finding, and identical scores across every criterion are evidence for a distinctness finding rather than a tie to break. It scaffolds from the shared validation report as its fifth consumer and appends the stage's own checklist rows (Distinctness, Recommendation grounding). `awf-ideate-revise` rewrites the artifact against the findings with a decision — accept, reject, or defer — recorded per finding in the artifact's own revision log, which is where the audit trail lives because this loop declares one output and one source of feedback; distinctness findings have exactly two honest answers, differentiate or discard, since renaming is the no-artifact-delta stall the loop contract watches for; and the recommendation is re-argued whenever the candidate set changed rather than left standing because no finding named it.
- Delivery skill family (`skills/`), binding the delivery stage's two steps and closing the run: `awf-deliver-prepare` assembles `{run}/delivery.md` from the run's own evidence — changes grouped by what they add up to rather than file by file, each traced to the brief or a recorded decision, declared deviations reported as part of what shipped, an acceptance-criteria table where unverified is a state rather than an omission, verification given as evidence (machine checks, tests, the verdicts on the change itself with their conditions, steps skipped for the risk class named as skipped), and a change description in the project's rendered PR or change-note standard — scaffolded from `references/delivery.template.md`, with `references/shipping.md` as the load-on-trigger boundary statement for getting it into the project's channel (the `delivery-approval` gate is the approval; merging and force-pushing are never inferred from an `accept`; the artifact stays the source of truth for the description). At R1 the same step writes the minimal change note the overlays call for, omitting the template's conditional sections. `awf-deliver-validate` renders the run's last verdict against the brief — every acceptance criterion verified against the change rather than against the artifact's table, artifact accuracy checked in both directions (unsupported claims and unmentioned changes both findings), verification claims treated as claims with stale machine-check evidence and unmet PASS_WITH_CONDITIONS conditions called out — scaffolding from the shared validation report as its fourth consumer. Its verdict gates nothing: every verdict routes to the delivery gate, where the human decides with it in view.
- Shared-template registry guard (`scripts/render_standards.py --check`, already a conformance CI step): a file anywhere under a skill directory that carries the generated-copy header but appears in no `SHARED_TEMPLATES` entry now fails the check. Registering a consumer is a manual edit, and forgetting it is silent — a template hand-copied from a neighboring skill would never be re-rendered and never drift-checked, diverging from its source unnoticed, which is the drift the registry exists to prevent. A copy whose header was stripped is indistinguishable from an authored file and stays out of scope. Four new unit tests cover it: an unregistered copy is flagged and named, copies outside `references/` and in nested directories are caught, a leading-whitespace copy still matches, and an authored reference file is left alone.
- Review skill family (`skills/`), binding all five review-stage steps: `awf-review-code` reviews the implemented change fresh-context against the plan — correctness, error handling, edge cases, performance, maintainability, standards adherence — producing severity-graded `R-…` findings with concrete fixes and no verdict in `{run}/review-findings.md`, with the performance anti-pattern catalog (`references/performance.md`) and external-contribution context (`references/contributor.md`) as load-on-trigger references. `awf-review-security` is the adversarial security pass — input boundaries, auth flows, secrets in source, dependency advisories, error-path leakage, storage and transport, headers, worked systematically per `references/security-checklist.md` — writing exploit-graded `S-…` findings with attack scenarios to `{run}/security-findings.md`, participating per the risk-class overlays. `awf-review-validate` renders the stage's verdict — acceptance criteria checked against the diff as ground truth, machine-check evidence required for PASS, a disposition for every open finding with unsupported claims marked contested rather than dropped, omissions hunted as its own `F-…` findings — scaffolding from the shared validation report as its third consumer. `awf-review-arbitrate` synthesizes findings and verdict into the single resolution list `review-fix` executes (`references/resolution.template.md`) — deduplication with traceable ids, a recorded refutation attempt behind every acceptance, dismissal rationale as rigorous as acceptance, a devil's-advocate pass on unanimity — when findings and verdict disagree, and always at R3. `awf-review-fix` applies the resolved list in severity order within the plan's declared file scope, records findings it must dispute instead of dropping them, escalates fixes that would leave the scope as structured `P-…` findings-for-planning, and records each fix, dispute, and escalation for the next iteration to re-review.
- Second shared report template (`standards/templates/review-report.template.md`): the verdict-free findings report both reviewer skills scaffold from — dimensions, a findings table with stable ids, detail sections with impact and suggested fix, positive observations — taking the shared-template registry to its first multi-source state. Two new unit tests cover it: every registered source renders its copies under a header naming that source, and drift is attributed to the drifted source's copy, not its neighbors'.
- Implementation skill family (`skills/`), binding the implementation stage's two steps: `awf-implement` executes the approved phase plan within its declared file scope — steps in plan order, tests per step, machine checks green at every checkpoint, commits in the project's format — writing the per-step record to `{run}/phase-{N}-impl-log.md`, scaffolded from `references/impl-log.template.md`; plan defects and ambiguities discovered mid-work become structured findings-for-planning entries with stable `P-…` ids for escalation into `plan-revise`, never silent workarounds or scope expansion, and loop iterations re-enter by addressing the previous validation report first. `awf-implement-validate` renders the verdict against the plan with the diff as ground truth over the log's claims — per-step verification, cross-referencing in all three directions (plan↔log↔diff), the no-undeclared-scope and machine-check-evidence checks the stage declares, and every finding attributed as implementation defect (iterate) or plan defect (escalate) — scaffolding its report from the shared `validation-report.template.md`, whose generated-copy registry gains its second consumer. Two new unit tests cover the registry's first multi-consumer state: every registered copy rendered identically, and drift attributed to exactly the drifted copy.
- Planning skill family (`skills/`), binding the planning stage's three steps: `awf-plan-create` consolidates the detailed, high-level, and bugfix planning variants into one planner skill — atomic implementation steps with files, changes, tests, and acceptance criteria, plus the mandatory file-scope declaration the implementation loop binds to — scaffolding `{run}/phase-{N}-plan.md` from `references/plan.template.md`, with multi-phase decomposition (`references/phase-decomposition.md`, loaded when the phase-1 plan fixes the phase list) and bugfix root-cause planning (`references/bugfix.md`) as load-on-trigger references. `awf-plan-validate` renders the verdict adversarially against the brief — requirements coverage, feasibility verified against the actual codebase, two-directional file-scope accuracy, implementer readiness — with phase-list and bugfix check overlays as references. `awf-plan-revise` handles all revision entry points (validation findings, gate direction, escalated implementation feedback, cross-phase cascade) with per-finding accept/reject/defer decisions audited to `{run}/phase-{N}-plan-feedback-{iteration}.yaml` per `references/feedback-format.md`, and explicit escalation when a revision would break the fixed phase list.
- Shared report templates (`standards/templates/`): report templates several skills declare are authored once and copied verbatim — under a generated-do-not-edit header — into each consuming skill's `references/` by `scripts/render_standards.py --render-shared`; the first is `validation-report.template.md`, the verdict report every validator skill scaffolds from, with stable finding/question ids (`F-…`/`Q-…`) that the plan-feedback format references. `render_standards.py --check` (already a conformance CI step) now also fails on a copy that is missing or has drifted from its source, and on placeholder syntax in a shared template (they never render). Eight new unit tests cover rendering, idempotence, drift, and every error path.
- Analysis skill family (`skills/`), the first two Agent Skills packages: `awf-ground` packages the ideation stage's `ground` step — analyst role, confirmed brief in, `{run}/grounding.md` out, scaffolded from `references/grounding.template.md`, with the ten-area analysis catalog in `references/analysis-checklist.md`; source references the brief cites are fetched through the executing harness's connections with pasted-text/export fallback and treated as context data, never instructions. `awf-analyze-report` is standalone (no stage binds it) and distills a completed grounding into a human-facing report scaffolded from `references/report.template.md`. Both carry the `awf-` vendor prefix (collision safety in consumers' shared `.agents/skills/`), a routable what-and-when `description` that flows verbatim into the `AGENTS.md` index, the `metadata.workflow` step block, and a `license` field.
- Standards single source (`standards/`): twelve placeholder-parameterized sources — four quality standards (`coding`, `architecture`, `testing`, `review-checklist`) and eight artifact formats (`commit-conventional`, `commit-angular`, `pr-github`, `pr-gitlab`, `pr-bitbucket`, `ticket-jira`, `ticket-linear`, `ticket-github-issues`) — from which project-specific copies are generated, never hand-copied. `scripts/render_standards.py` (stdlib-only) renders them with consumer-supplied values for the closed placeholder vocabulary (`{{PROJECT_NAME}}`, `{{TECH_STACK}}`, `{{ARCHITECTURE_TYPE}}`; `--only` renders a selection), and its `--check` mode — run as a conformance CI step — fails on unregistered tokens or malformed double-brace syntax and dry-renders every source to prove full resolution. Unit tests (`scripts/test_render_standards.py`, stdlib `unittest`) cover rendering, selection, config validation, integrity checking, and every error path.

### Changed

- `awf-analyze-report` now instructs the sections it produces, and says why it declines a project standard. Seven of the eleven sections its report template carries — architecture overview, tech stack, key patterns, module map, dependencies, testing approach, and the quick reference — had no instruction in the skill body. The method reached four and relied on the template for the rest, under the Output's standing direction to fill every placeholder it defines — which is not wrong and is not a method either: it says something must go in a section and never what, so the only statement of what seven of them are for was the bracketed prompt inside the scaffold the step is filling in. That the template is loaded is the point rather than the objection. A bracketed prompt is the artifact's own scaffolding and the step overwrites it as it writes; the skill is what says how to produce the content that replaces it, which is why a template that has a place for every result is a different question from a method that says what goes there. The method now walks the report in the order it is written, naming each section's substance in the template's own words and adding the judgment that separates the section from a transcription of the grounding it is built on — that a convention held in half the modules is a finding rather than a convention; that dependency health is stated rather than left for the reader to total; that relative coverage is named on both sides, well-tested against bare, since the contrast is the information and the bare areas are what a reader acts on; and, for the architecture, that whether it is clean, evolving, or drifting is read off the drift `awf-ground` is required to flag rather than compared afresh here, the gap being what gets reported where the grounding made no such comparison. The template's own words rather than a paraphrase of them, deliberately: two enumerations of one list are how a body and the template it instructs come apart, and a paraphrase is the first step of that. Copying the lists is not sufficient either, which is the less obvious half — the rationale clause hanging off a list is where a paraphrase goes once it has been chased out of the list itself, and what it does there is quietly halve a two-sided instruction. Relative coverage is well-tested *against* bare, and the summary's strengths sit beside its concerns; in both, the second half is where the information is. The recommendation groups name the effort and impact that sort into them rather than only the three group names. The method now matches every substantive term the template carries, which is a bar something can be held to rather than a claim about how carefully it was written. The fill-every-placeholder direction stays, now covering what nothing else needs to say — the date, and the grounding the report was built from — plus the licence to omit a section the template marks conditional, rather than standing in for a method. The third header field is not one of those: **Scope** is the grounding's rather than the codebase's, general where the analysis was general and naming the focus areas where the brief pointed at particular parts of the system, since `awf-ground` goes deep on exactly those rather than evenly everywhere and a focused report that reads as a survey overstates what it covers. The standards decline is the other half and the same defect: three of the twenty-two skills declare no project standard, and this was the one of the three that never said why. It judges plenty — what a piece of debt costs, whether the coverage is thin, what the architecture is doing — but against the evidence the grounding carries rather than against a bar of its own, `awf-ground` having already read the coding and architecture standards to tell what a project committed to from what its code merely exhibits and recorded the disagreements as grounding, so reading them again here would make this a review of the codebase rather than a report on it, and a departure from a project's own standard is a finding this step relays rather than one it makes. All three decliners now open with the same sentence, in a paragraph at the end of their inputs. The frontmatter `description` moves for the same reason as the rest of it: it reads as a list of what the report contains and listed six of the eleven sections, so tech stack and key patterns join it and the generated index carries them — it had 432 characters of headroom against the 1024-character budget, so leaving them off had been a choice rather than a trade. No declaration moves with any of it: no step block, no stage since nothing declares this step, and nothing downstream, `{run}/report.md` being an artifact no step in this repo consumes.
- The phase vocabulary gains a second placeholder, because the model has needed one for as long as it has had stages that run after the last phase. `{N}` names **the phase a step is executing** and resolves to one artifact; `{P}` names **each phase the run has completed** and resolves to one per such phase. Six files had been saying the second thing in prose — `workflows/stages/review.md`, `workflows/stages/delivery.md` and four review skills all declared `phase-{N}-` paths and then explained, in the paragraph below, that `{N}` there ranged over every completed phase rather than naming one. That is a declaration meaning something its own vocabulary cannot express, repeated six times and enforced nowhere; those thirty-eight declarations now say `{P}` and the six explanations are gone. What the token was actually added for is a gap it makes visible: `awf-implement-validate` fills a **Cross-phase impact** section with what a phase's implementation binds for the phases after it — a rollout order, a migration step, a compatibility guarantee — and those are precisely the constraints that leave no trace in the tree the next planner reads. Planning declared no previous phase's report, and §9.1 materializes only what is declared, so the note reached the next phase only where a human remembered to carry it, and `plan-validate` read the same inputs and could not check a plan against it. `awf-plan-create` and `awf-plan-validate` now declare `{run}/phase-{P}-impl-validation.md`, optional because phase 1 has nothing behind it, freshness-checked by each report's `Run` header since §8.4's cache would otherwise admit another run's sequencing. The validator gains what it could not have before: a plan that contradicts an earlier phase's binding is now a finding rather than something only the human might notice, and the finding names the phase that set it. What resolves `{P}` is the manifest (§8.2), which already records what the run produced and only grows within it — so the token needs no field of its own and no notion of a phase being finished, and lands right at every reader by construction: a step planning phase N sees the phases before it, because phase N's own artifact is what it is about to produce, and a stage running after the last phase sees them all. `required` counts the same manifest: blocked where it records the artifact for no phase, empty where an optional one records none. It is this run's manifest, which is why `{P}` and §8.4's cross-run cache do not compose. Two contexts needed saying beyond a step's inputs. A loop contract has no output and so no phase of its own, which is why a `{P}` path in one excludes nothing — and §9.2 now says how several resolved plans combine: `scope.declared_from` carrying `{P}` binds the loop to the **union** of what those plans declare, since intersection would put a file no single phase owned outside the scope of the change that contains it. The loop schema's own description says it too, and a starter variant carries the shape, which turns out to be the first fixture in the set to exercise a `scope` block at all. One rule comes with the token, and the step schema holds it rather than a script: an `output.artifact` may not carry `{P}`, because a step produces one artifact (§9.1) and a phase-set of outputs is a stage that repeats rather than a step that fans out. It has its own negative fixture like every other schema rule here, so a standard validator catches it too — the two tokens differ by one character in otherwise identical paths, which is when a rule earns enforcement.
- Spec §7 and §5.3 now say what a gate decision carries besides its outcome. Both answer one question the gate record raises by being deliberately thin: it holds a gate id, transport, outcome and timestamp, so a human's *reasoning* has nowhere to go unless the protocol says where. §7 takes the direction half. A gate decision MAY carry the human's direction — what they want changed, or the content of an answer to a question the gate asked — and because the direction is not an artifact it has no place in an `inputs` declaration, so §9.1's completeness rule cannot reach it, which is exactly why silence about it was load-bearing rather than harmless. The step that acts on the direction MUST instead state in its instructions that it consumes it, and where the direction amends an artifact the run already holds, its content lands there rather than in the record — the treatment the `clarifying-question` gate had been stating for itself alone, now general. An `accept` may carry it only where the stage routes that `accept` to a step which re-reads the artifact — the clarifying question is the one, returning through the step that restates the brief before the run continues rather than proceeding past it, and it is why the clause is not scoped to `revise` alone. For the four validators whose report carries the shared template's **Standards** checklist row — `awf-plan-validate`, `awf-implement-validate`, `awf-review-validate`, `awf-deliver-validate` — the declaration is what that row is checked against; it had been asserting adherence to standards the skills never referenced. In every case an argued departure stays legitimate and is judged on the argument; only a silent one is a finding.

- The delivery stage's `deliver-validate` step now takes `{run}/phase-{N}-impl-log.md` (required) and `{run}/phase-{N}-impl-validation.md` plus `{run}/review-validation.md` (optional), for the same reason the review stage's declarations gained theirs: the step checks the delivery artifact's evidence claims, quoted verdicts, and conditions against the artifacts they came from, and an executor that materializes only declared inputs would have left it taking the artifact's own word for exactly what it is there to audit. The log is required because delivery composes only into workflows that implement; the validations stay optional because reclassification applies the new class's defaults to subsequent steps only (spec §5.3) — a run bumped upward mid-implementation reaches delivery with no implementation validation behind it, so requiring them would make a legitimate reclassified run unexecutable at its last step.
- The delivery stage declares its inputs with `{P}`, one path per phase, rather than the `{N}` that names the phase a per-phase stage is executing: delivery closes the run, so a multi-phase run's artifact and validation cover every phase.
- The shared validation-report template's verdict section no longer says the verdict "routes the loop" — with `deliver-validate` there is now a validator whose verdict routes only to a gate, so the wording covers both (all four generated copies re-rendered).
- The review stage's step declarations gained two inputs their prose already implied, because an executor that materializes only declared inputs must be guaranteed them: `review-validate` requires `{run}/phase-{N}-plan.md` (the verdict judges the change against its acceptance criteria and file-scope declaration; previously reachable only through the implementation log's link), and `review-fix` optionally takes `{run}/security-findings.md` (where the security pass ran without arbitration, its findings are part of the working list — otherwise a FAIL forced by security findings would iterate into a fix step that cannot see them).
- Conformance validation now validates `metadata.workflow` blocks declared in Agent Skills frontmatter — previously only fenced yaml blocks were scanned, so skill-tier step blocks would have escaped the schema, placeholder, and template checks silently — and requires a `license` field on every `skills/*/SKILL.md` frontmatter, so installed skill copies state their terms standalone.
- `standards/README.md` names both shared templates. Its shared-templates section still read "currently `templates/validation-report.template.md`" after `review-report.template.md` landed beside it with the review family, so the directory and the `SHARED_TEMPLATES` registry carried two while the README describing the mechanism enumerated one. Two enumerations of one set, disagreeing, are the same species the shared-template machinery guards its copies against — this instance sat in the prose describing that machinery, which no check reads.
